# Trio64 ROM (764): fixes and improvements

What 1.5-07-pN (the level in [`common/version.inc`](../common/version.inc), now p4) changes against the Phoenix S3 Trio64 BIOS
1.5-07, each with the issue that has the details. The speed patches, the booster and the flip-flop reset
are backports from the Trio64V2 ROM ([`docs/775-changes.md`](775-changes.md)); their issues are the Trio64V2 ones, which
carry the label 764. The build, the space map, the base candidates, the MCLK survey and the
card runs are in [`docs/764-rom.md`](764-rom.md).

| Change | Level | Issue | How |
| --- | --- | --- | --- |
| No interlaced defaults | p1 | [#68](https://github.com/perchrh/trio64-vbios-tools/issues/68) | The 11 refresh entries that run interlaced (CR42 bit 5, found by setting every mode at every refresh index in the emulator) are removed. The modes that also have non-interlaced rates (1024x768 and 1280x1024 at 8, 15 and 16 bpp, and the 2xxh modes 204h, 205h, 208h with the same timings) now default to their lowest non-interlaced rate: 1024x768 at 59.8 Hz (65.3 MHz), 1280x1024 at 60.3 Hz (112.2 MHz, clock-doubled). |
| Interlaced-only modes removed | p1 | [#68](https://github.com/perchrh/trio64-vbios-tools/issues/68) | 106h (1280x1024x4), 118h (1024x768x16M), 119h and 11Ah (1280x1024x32K/64K) and 120h (1600x1200) exist on the Trio64 only interlaced (1600x1200 at 60 Hz needs 162 MHz, the chip maximum is 135 MHz; the others need clocks above the single-clock limits for their depth, CLK-1). They are gone from the mode table, both VESA lists (4F00 no longer lists them, 4F02 refuses them with 014Fh) and the mode map. Kept removed by decision (1 November 2026), although drivers written for the 86Box Trio64 (the same Phoenix ROM) offer 118h and 11Ah on 4 MB cards: restoring 118h-11Ah would take about 165 bytes, all five about 305, against about 75 free; drivers should check 4F01 attribute bit 0 instead (suggested to velocity9x). |
| 800x600 at 60 Hz | p1 | [#68](https://github.com/perchrh/trio64-vbios-tools/issues/68) | POST writes CR52 = 80h instead of 00h: the refresh index of the 800x600 modes is 1, the 60.7 Hz entry (VESA DMT, line total 1056) instead of 56 Hz. Phoenix writes CR41/CR52 only at POST; a refresh utility can still choose another rate. |
| 32-bit speed patches | p1 | [#61](https://github.com/perchrh/trio64-vbios-tools/issues/61), [#62](https://github.com/perchrh/trio64-vbios-tools/issues/62), [#51](https://github.com/perchrh/trio64-vbios-tools/issues/51) | VGA mode set clear, font load, mode 13h scroll (with EAX kept), text and planar scrolls, AH=09h: the shared `speed_sites` and .asm files, the same signatures as in 2.04.07 and 1.03-08. |
| Booster with the Windows check | p1 | [#47](https://github.com/perchrh/trio64-vbios-tools/issues/47) | On after a banked 4F02 and at the window set with BH = 0 (4F05 and the window function both call Phoenix's window set at 5123h). The refusal mark is CR52 bit 3 (`tbon.asm` says why not CR6C or CR6D). Phoenix relocks the S3 registers after its calls and its unlock routine changes AX, so the code unlocks itself and leaves CR38/CR39 as found. |
| S3's fonts | p1 | [#69](https://github.com/perchrh/trio64-vbios-tools/issues/69) | All five font tables of 1.03-08 (byte for byte those of 2.04.07, the Trio64V2 card's) replace Phoenix's: 8x8, 8x14, the 9x14 alternate table, 8x16 and the 9x16 alternate table, end to end from 5720h to 7F90h. S3's 9-dot alternate tables have 20 and 19 entries, Phoenix's 18 and 17, 63 bytes more in all: the 8x8 and 8x14 fonts and the 9x14 table keep their addresses, the 8x16 font moves from 6E30h to 6E4Dh and the 9x16 table from 7E30h to 7E4Dh, and Phoenix's eight references to these two (six mov bx/si and two words of the AX=1130h table at 315Ah; riplin names no others) are rewritten with byte assertions. The mode 13h scroll moved behind the fonts and its window path to 0130h (below). No hardware reason against the transplant: the BIOS copies the glyphs into plane 2 as on every VGA. |
| ATC flip-flop reset | p1 | [#52](https://github.com/perchrh/trio64-vbios-tools/issues/52) | In the mode set hook (AH=00 table and 4F02's call). |
| VDIF deleted | p2 | [#75](https://github.com/perchrh/trio64-vbios-tools/issues/75) | For space (31 October 2026). VBE 4F15 BL=02h, read VDIF (a format VESA withdrew), now fails with AH=01h at once; 1.5-07 first spent the 50-frame DDC1 watch on it. Its routine (52E1h-5341h, 97 bytes) is zeroed (`DDC_FREED`), and two sites with byte assertions (`DDC_SITES`) end BL=02h at the dispatcher, so nothing refers to the freed code. DDC1 and DDC2B stay byte for byte as in 1.5-07: Windows 95 Plug and Play (BL=00h, then BL=01h) reads the EDID of DDC2B monitors and of the era's monitors that speak DDC1 alone, so DDC1 is kept by decision (31 October 2026), although its detection is what makes 4F15 take about 0.73 s without a DDC monitor. |
| Sequencer index kept by 4F05 | p1 | [#67](https://github.com/perchrh/trio64-vbios-tools/issues/67) | Phoenix's window set (5123h) and get (5148h) read SR04 (chain 4) and left the 3C4h index at 04h. Both reads now go through `sr04` (`twin.asm`), which reads SR04 and writes the index back as found, for 4F05 and the window function, BH = 0 and 1. The data book does not require it (it defines the registers, not what a BIOS call leaves in an index); S3's own 2.04.07 and 1.03-08 leave the index as found, and S3TEST's 4F05 line expects that (fail bit 2). |
| MCLK build option | p1 | [#112](https://github.com/perchrh/trio64-vbios-tools/issues/112) | `MCLK=` sets the single MCLK entry at 3B5h, up to 70 MHz, the limit our tools take for the Trio64 (T64-MEM-7; the data book gives 60 MHz, MEM-1); above 70 MHz only with `OVERCLOCK=1`; without it the build's own clock stays. |
| Display FIFO M from the bandwidth | p2, p3 | [#75](https://github.com/perchrh/trio64-vbios-tools/issues/75), [#82](https://github.com/perchrh/trio64-vbios-tools/issues/82) | Phoenix writes CR54 (M, bits 7-3) from its mode table, values chosen for its interlaced defaults and a faster MCLK; with the 60 Hz defaults and 54.9 MHz the FIFO ran dry in windowed video at 800x600x16 (M = 19). `fifo` (`tfifo.asm` in the 97 bytes of the deleted VDIF code, `tfifo2.asm` in the sign-on padding 00AEh-00E3h) runs in the mode set where Phoenix writes CR67 (DCLK, CR3A and CR54 are set by then, the screen still off) and in the packed modes (CR3A bit 4) lowers M to (t - 23) / 6, t = 112 x MCLK / (DCLK x bytes per pixel): the MCLKs in which the display drains 112 of the FIFO's 128 bytes, less two entry cycles of 9 MCLKs and one access, at 6 MCLKs per access (the data book: 2 per page cycle, 6-9 per entry cycle; the card streaked at M = 19 with 54.9 MHz and not at 69.8 MHz, which puts the mean between 3.5 and 4.7). p2 counted 5 MCLKs per access; after its white dots at 60 MHz on the card ("On the card") p3 counts 6 ([#82](https://github.com/perchrh/trio64-vbios-tools/issues/82), open until a card run at 60 MHz; the 60 MHz result does not fit a pure bandwidth model, see the issue). Phoenix's own Vision864 BIOSes (1.03-08, 1.04-01, 2.00-01, PCI 5333:88C1; the Trio64 integrates the Vision864, uploaded 31 October 2026) write a fixed M per mode class: 23 in the 8 bpp modes, 11 in 800x600x16 (113h/114h), 15 in 1024x768x16, 5 in 800x600x24; Phoenix 1.5-07 raised 114h to 19, the value that streaked, and the computed M (8 to 12 in 114h) is close to the Vision864's 11. It never raises M. 112 x MCLK in kHz is a constant in the code that the patcher writes from the build's MCLK pair, so `MCLK=` builds follow. At 54.9 MHz in the emulator (p3): 103h 31 to 21, 105h 31 to 11, 107h 26 to 5, 112h 7 to 6, 113h/114h 19 to 8, 115h 4 to 2, 116h/117h 5 to 4; 101h, 110h, 111h and the VGA modes unchanged. In 114h: M = 8 at 55 MHz, 10 at 60 MHz, 12 at 69.8 MHz (p2: 10, 12, 14). |
| The 32 KB twice in the 64 KB image (the DSP-3364P maps the upper half) | p1 | [#78](https://github.com/perchrh/trio64-vbios-tools/issues/78) | `SIZE764=32` for a 32 KB EEPROM. |
| Two Trio64 models: `make 764x-rom` (86C764X, MCLK 55-70 MHz) and `make 764p-rom` (86C764-P, 50-60 MHz) | p3 | [#112](https://github.com/perchrh/trio64-vbios-tools/issues/112) | The same ROM; the models differ in the clock range the build option accepts (T64-MEM-7). |
| No monitor sense at POST | p4 | [#134](https://github.com/perchrh/trio64-vbios-tools/issues/134) | As in S3's Trio64V+ BIOS 1.03-08N. Only the call of the sense (025Fh, call 0263h) becomes `xor bx,bx`, the colour result: POST no longer turns on grey-scale summing for a display that reads as monochrome, and no longer beeps when none is found. The configuration bit (0199h bit 1) is not used, because it skips the whole routine at 1033h, its CR38/CR39 unlock and mode set 03h too. |



Not applied: the fast 4F05 path ([#59](https://github.com/perchrh/trio64-vbios-tools/issues/59): Phoenix's 4F05 is short: 6 OUTs for a bank in 101h in the emulator, 14 in our ROM with the booster check and the sequencer index kept), the 32-bit S3/VESA
mode set clear ([#60](https://github.com/perchrh/trio64-vbios-tools/issues/60): Phoenix clears with the graphics engine; open, [`docs/764-rom.md`](764-rom.md) "Pending"), the base restore (Phoenix writes CR59 from
CR6B and CR5A from CR6C bit 7 at every mode set), the PLL N = 0 fix (the N = 0 entries were the
interlaced 1280x1024 ones, now removed), the Trio64V2 register fixes and VBE 2.0.
