# The Trio64V2/DX ROM (775): 2.04.07-p28

Our ROM for the S3 Trio64V2/DX (86C775) and Trio64V2/GX (86C785), PCI 5333:8901: the S3 reference BIOS
2.04.07 with the changes below, built by [`src/roms/s3patch.py`](../src/roms/s3patch.py). The test card is the Gainward GW503A
(Genesis EV), 2 MB EDO 40 ns, whose stock BIOS is S3's 2.04.11. The level is `VER775` in
[`src/tools/common/version.inc`](../src/tools/common/version.inc). The other two ROMs are described in [`docs/765-rom.md`](765-rom.md) (Trio64V+) and
[`docs/764-rom.md`](764-rom.md) (Trio64); the speed measured on the card is in README "Speed".

## The reference image

`reference/775/2_04_07.bin`, 32 KB, SHA-256 25d64cd7...:

- "S3 86C775/86C785 Video BIOS. Version 2.04.07", "Copyright 1996 S3 Incorporated. 50", dated 05/20/97
  (twice, at 00AAh and 00B2h): S3's reference BIOS, one image for the Trio64V2/DX and the Trio64V2/GX.
- PCI 5333:8901.
- MCLK 50.11 MHz at POST (SR10/SR11 = 41h/28h, bytes 00C7h-00C8h; our ROM keeps it, and since p26 also
  writes it into the fast page entry 00C9h and the SGRAM entry 00CBh; p9-p25 loaded 59.96 MHz). The
  "50" after the copyright line matches it; that it is meant as an MCLK tag is not established.
- VBE 2.0, with linear frame buffer modes. 4F15h has the DDC delay latch bug that S3's 2.04.11 fixes
  (our p19).
- The test card's own BIOS is 2.04.11, a later S3 build of the same code base. Its MCLK on the card is
  50.11 MHz as well, not 60 MHz: its POST picks the entry by CR36 bits 3-2 with the same code at 14A5h,
  and the entries are 00C7h 28h 41h (1-cycle EDO, 50.11 MHz), 00C9h and 00CBh 48h 42h (fast page and
  2-cycle EDO, SGRAM: 66.22 MHz). The card is strapped for 1-cycle EDO (CR36 = 92h), so POST loads
  50.11 MHz (checked in the GW503A dump, SHA-256 04514208..., 7 November 2026). No entry is 60 MHz;
  59.96 MHz on the card was our ROM's choice from p9 to p25, the data book's 1-cycle EDO maximum
  (V2-MEM-1); since p26 the default build runs 50.11 MHz, as 2.04.11.
- Neither 2.04.07 nor 2.04.11 is on theretroweb as of 1 November 2026; both are to be uploaded there.

## The build

[`src/roms/`](../src/roms/) holds the code the ROM carries (nasm sources, assembled at their ROM offsets, with the
2.04.07 addresses they use in `bios.inc`) and `s3patch.py`, which applies the whole current change set
(level p28) to the S3 reference BIOS 2.04.07. It needs python3 (no packages) and NASM:

    python3 src/roms/s3patch.py reference/775/2_04_07.bin -o S3V2P28.BIN
    make 775-rom OUT=S3V2P24.BIN

The input is the 32 KB reference BIOS (or a 64 KB image with it in the lower half; the rest is not
used). The repository carries it as `reference/775/2_04_07.bin`, the default of `IN` for `make 775-rom` and
of `REF775` for `make 775-rom-test` and `make 775-ref-compare`; `IN=...` or `REF775=...` selects another copy. The
result is 64 KB: the patched 32 KB twice, as in the Trio64 and Trio64V+ ROMs (#78, README "Trio64 ROM"; p15 to
p21 were first built with 32 KB of zeros above). Only 2.04.07 is accepted. Every patch site is
compared with the original code first (the replaced routines in full), and the result is checked
before it is written: the lower half sums to 00 and declares 32 KB, the upper half is a copy of it, every
DCLK VCO is in the data book's 135-340 MHz, and with the known reference image the SHA-256 of the lower 32 KB is the one
of the build that passed every emulator test (0fa6ab97...).

That SHA-256 holds for NASM 3.02, the assembler of the project. Another NASM version may encode some
instructions differently (NASM 2.16.01 puts the REP prefix before the operand-size prefix of REP
MOVSD/STOSD, 3.01 and 3.02 after it; such an image works the same), and then the result check fails: s3patch names the assembler and the blocks whose
code differs from the tested build, writes nothing to OUT and keeps the image in OUT.untested, only
for a comparison; do not flash it. Build with 3.02 instead, for example
`make 775-rom OUT=S3V2P24.BIN NASM=nasm/nasm-3.02/nasm`.

    python3 src/roms/test_s3patch.py --ref reference/775/2_04_07.bin [--stock STOCK.BIN] [--rom S3V2P24.BIN]
    make 775-rom-test [STOCK=STOCK.BIN] [ROM=S3V2P24.BIN]

runs the checksum tests: the pinned SHA-256 (and the same bytes as `--rom`), the lower half sums to
00 with the right byte at 7FFFh, the upper half a copy, the VCO range, every refresh entry with M 1-127,
N 1-31 and a defined R code (pllcodes), the free bytes still 00, a 64 KB
input giving the same result whatever its upper half holds, and the inputs that must
be refused (already patched, three patch sites changed, a wrong checksum, and with
`--stock` the card's stock 2.04.11), and the MCLK build option (mclk; README "MCLK build option").

## On the card: 2.04.07-p27 with MCLK=60 (11 November 2026)

The `MCLK=60` build of p27 on the Trio64V2/DX test card (PCI 8901 rev 06, CR36 = 92h, 2 MB 1-cycle EDO;
SR10/SR11 = 42h/41h = 59956 kHz, not the 50.11 MHz default of p26+), RUNALL.BAT with the tools of
1.0.1-5578afc38, now with `vgalog /M /XL` before every tool and REPORT packing the rings (#224, #227).
The bundle is `results/86C775.ZIP`. p27 is the GETCRTC fix (#195, for #193): the fast 4F05 set window
takes the CRTC port from MISC bit 0 instead of a hardcoded 3D4h, so it also reaches 3B4h in the mono
modes. VGASHOW (#225) ran on the card for the first time.

- **S3TEST:** 40 PASS, 0 FAIL, 0 SKIP: signature 2.04.07-p27, checksum 00, MCLK 59956 kHz (chip max
  60000), SR1A 1Fh, CR41/CR52 88h/81h, every mode line at its expected rate and line total, the banked
  320 KB data check with 0 errors, 4F06 BL=3 4368/4368. Banked write throughput 74606 KB/s (threshold
  60000); 4F02 101h with clear 39.1 ms; 4F05 set window 19.1 us. The .DBG ends `D:END lost=0`.
- **S3COMPAT:** 240 PASS, 0 FAIL, 16 WARN, 12 INFO, 4 SKIP, all WARN/SKIP the known items of "Known
  remaining items" (no 8x14 font, the MDA DAC#01 lines, AH=12h BL=20h, 012Eh/010Fh/0131h/0134h WARN 80,
  012Ah WARN 82, 104h LFB on planar, 106h at 108 MHz). The mono check of #193/#215 ran on the card and
  passed: the MDA 07h/0Fh lines (pass 1 and pass 2) show no FAIL 80, and the .DBG has AX=4F05 BX=0 DX=2
  right after each AX=0007/000F mode set with MISC=66 (mono, CRTC at 3B4h) and the CR6A readback through
  3B4h non-zero. The p27 fast 4F05 works in the mono modes on the device; #193 is closed as verified on
  the card. The .DBG ends `D:END lost=0`.
- **VBESHOW /R:** every mode that fits 2 MB at its intended rate; 0109h/010Ah (text) and
  0118h/0164h/0119h/011Ah (need more than 2048 KB) skipped with the 4F00 memory size.
- **VGASHOW /R:** every standard mode 00h-13h measured at its rate (69.7 Hz at the 400-line modes,
  59.6 Hz at 11h/12h, 31.2 kHz), the mono 07h through 3B4h.
- **S3REGS before and after each tool:** mode 03 at both ends, SR10/SR11 = 42h/41h throughout, PCI
  subsystem 89015333, LFB E4000000; after the tests CR91 = C7h, the L1 leftover of 120h as designed
  since p25 (#166).
- **VGALOG /M /XL:** the four per-tool rings (VGALOG0.BIN to VGALOG3.BIN, VGALOG0 the full 128 KB ring)
  and the one-call VGALOG.BIN (a single 4F03); every header carries chip 8901 rev 06 E1, CR36 = 92h,
  SR10/SR11 = 42h/41h and the ROM string 2.04.07-p27, so the ROM never touched MCLK during the runs;
  no call hung.
- **Open point:** banked write throughput 74606 KB/s at 59.96 MHz against p24's 82374 KB/s at the same
  clock (p25 at 50.11 MHz: 74120 KB/s), while 4F02 101h-with-clear is unchanged (39.1 against 38.9 ms).
  The p27 GETCRTC change costs one port read per 4F05 call, about 0.1 % of the bench (one call per
  64 KB block), not the cause. To tell a real p25-p27 regression from run-to-run variance, an A/B on
  the card is needed: same tools, same boot, S3TEST on a p24 ROM and on p27, both at MCLK=60.
- **Side note:** the printed VGA fail-bit legend ([`src/tools/s3compat/s3compat.asm`](../src/tools/s3compat/s3compat.asm)
  line 293) still lists only bits 1-40; bit 80 (4F05 in a mono mode, #193) is documented only in the
  source comment at line 944 (#230).

## The VIDSPEED run

The speed results of VIDSPEED on the card, stock 2.04.11 against 2.04.07-p21 (31 October 2026), are in
README "Speed". What else the run showed:

- **Refresh lines:** 1280x1024 runs at 60.26 Hz (61.65 kHz) instead of the stock's interlaced 86.89 Hz
  (44.47 kHz), and the 640x480 modes at 28.65 kHz (800 pixels per line) instead of 28.79-28.94 kHz: the
  60 Hz defaults and the 800-pixel line. The 132-column text modes (VESA 109h/10Ah) at 28.09 kHz and
  800x600 at 36.28 kHz instead of 28.00 and 36.17 kHz: 2.04.07 programs 40.09 MHz where 2.04.11 has
  39.97 MHz (SR12/SR13 63h/6Eh against 61h/41h), 0.3 %; a difference of the base BIOS, not of a patch.
- **VGALOG /M during the p21 run** (all 330 INT 10h calls): after every banked 4F02 of a packed mode
  CR58 = 90h and CR59/CR5A = 000Ah (the booster on), after the planar modes 102h, 104h and 106h CR58 =
  83h and E000h (off), and every return to mode 03h puts E000h back. VIDSPEED never calls 4F05: it
  switches banks without INT 10h, so it gets the booster only because p18 switches it on at the end
  of 4F02 (with p16 and p17, which waited for the first 4F05 or window function call, it would not).
  The other calls (VIDSPEED's DESQview and chipset probes, 4F01 of every listed mode, the BIOS's own
  AX=1130h inside the mode sets) return as they should.

### Reproducer programs: the card and 86Box agree (12 November 2026)

The small reproducer .COMs written for the 86Box issue reports were run on the card (Windows 98 DOS
prompt) and in 86Box. 86Box matched the card in every case; the BUG verdicts came from reference
values that were not the card's, not from the emulator:

- `pci-ssid`: PCI config 2Ch-2Fh reads `89015333` on the card and in 86Box. CR81-CR84 read `33 53 01 89`
  through 3D4/3D5 - the ROM bytes at C000:0040-0043, which the video BIOS copies to CR81-CR84 and
  which PCI 2Ch-2Fh then shadow (chip-rules V2-PCI-1, V2 data book 3.8). The option ROM's PCIR
  carries a different subsystem ID (3719:3303 at PCIR+0x18/0x1A), but the card does not put that into
  config space - on real hardware either. The reproducer's EXPECT was taken from the PCIR, hence
  its BUG.
- `vga-regs`: mode 00h reads SR04=09h and mode 07h reads DAC entry 01 as `09 09 09`, on the card and in
  86Box alike. The reproducer's EXPECT (02h, 050505) is the IBM VGA reference (VGATEST); the S3 BIOS
  programs its own values in those modes, so an S3 card is compared against the card, not against
  IBM VGA.
- `vberef`: on the card it prints `HZ10=0 EXPECT=597 STATUS=BUG`, the same shape as in 86Box (0 or
  about double). The reproducer is at fault here, not the card: its HZ10 formula divides by
  TICKS*10000, so it prints Hz rather than Hz x 10 (a perfect 59.7 Hz run would print 59 and still
  say BUG against its 560-640 window), and it checks the deadline only after a counted edge, so the
  hardware run counted about one edge in ~2 s and printed 0. Mode 101h on this card is the standard
  640x480x8 at 59.7 Hz (VESA DMT). The corrected probe `vbe2` (counts edges with the deadline checked
  every iteration, measures text mode 03h and VBE 101h, prints EDGES/TICKS/HZ10) is the one to use for
  a hardware refresh number; in 86Box the 0/~2x reading is the virtual clock (86Box issue #8). See
  [docs/86box-runs.md](86box-runs.md).
- `vbe4` (vsync edges on 3DAh bit 3, timed by the PIT channel-0 counter latch at 1.193182 MHz instead
  of the BDA tick, ~2 s per mode): on the card, mode 03h prints `EDGES=68 PITC=2359300 HZ10=343` and
  mode 101h `EDGES=59 PITC=2359302 HZ10=298`; in 86Box 7.0 the same binary prints
  `EDGES=69 PITC=2359300 HZ10=348` and `EDGES=59 PITC=2359298 HZ10=298`. Card and 86Box agree within
  1.5 %, so under this probe the emulator's PIT/vsync model matches the card. The earlier zeroes came
  from the reproducer reading the BDA tick (0040:006C), which does not advance during a tight
  port-read spin - in 86Box and in the Windows 98 DOS box alike. The HZ10 reading is about half the
  nominal mode rate (70 Hz for 03h, 59.7 Hz for 101h, VESA DMT) on card and emulator alike: the poll
  samples 3DAh once per eight loop iterations plus a PIT latch (~0.1 ms between samples) and aliases
  against the vsync pulse, so about every other pulse is missed - a property of the probe, not of the
  emulator (86Box issue #8).

No code was copied from another project; the ROM code was written for this BIOS, except the DDC delay
(`ddcwait.asm`), which reproduces the routine of S3's own BIOS 2.04.11, the same vendor and code base
as the reference 2.04.07 the ROM is built on.

| Item in the ROM | Origin | What was taken |
| --- | --- | --- |
| FIFO fetch fix | [S3VBEFIX](https://github.com/wbcbz7/S3VBEFIX) 0.6.1 by Artem Vasilev (wbcbz7), WTFPL | The diagnosis and the fix: clear CR90 bit 7 when a VGA mode is set (p7: every 00h-13h; p25: mode 13h only, [#166](https://github.com/perchrh/trio64-vbios-tools/issues/166)) |
| Attribute flip-flop reset | S3VBEFIX | The idea: a dummy read of the input status register (3DAh) after the mode set |
| Booster | S3VBEFIX, which credits SVGATRIX.TXT; the 64 KB linear window at A0000h is documented in the Trio64V+ datasheet | The register sequence CR58 AND ECh, CR59=00, CR5A=0Ah, CR58 OR 10h. Saving the real base in CR6D and restoring it in the ROM's own mode set is our design |
| LFB mode set handling | S3VBEFIX | Only the observation that the booster's base must be restored before an LFB mode; implemented differently |
| Memory clock 50.11 MHz in every entry (p26) | S3 2.04.07 and 2.04.11 | Their 1-cycle EDO PLL pair, 28h 41h (p9-p25: 59.96 MHz, chosen to meet the 16.67 ns 1-cycle EDO limit of the Trio64V2 datasheet) |
| DDC fixes, CR23 before CR26 | S3 BIOS 2.04.11 (the card's stock BIOS); Trio64V2 datasheet section 4.2 | The DDC delay routine, the probe's count in AX and interrupts off during 4F15 as in 2.04.11; CR23 = 00h before CR26 on every mode set (2.04.11 does it only after modes above 13h) |

## Not taken from 2.04.11: AX in the 4F0A protected-mode code

The S3 BIOS 2.04.11 (the card's stock BIOS) saves AX in its VBE 4F0A protected-mode functions (set
window, display start, palette) and restores it before the return. 2.04.07, and so this ROM, returns
AX = 004Fh from them, the real-mode status. The ROM keeps that:

- VBE 2.0 section 4.13: "Currently undefined registers may be destroyed with the exception of ESI,
  EBP, DS and SS". AX has no defined output there, so both conform.
- A program that checks AX = 004Fh after the call, as after INT 10h, works only with 004Fh returned;
  with AX kept it gets its own AX back, often 4F05h, because callers load the same registers as for
  the real-mode call. Only a program that relies on AX surviving, which the specification does not
  allow, gains from 2.04.11's change, and none is known.
- Warcraft II switches banks through this code and works with the ROM.


## Not used: the S3 OEM functions (4F14h) of later BIOSes

The S3 OEM functions of 2.04.11, the Trio3D BIOS 2.0B.10 and the Trio3D/2X BIOS 2.0C.10 were compared
with this ROM's (2.04.07) on 30 October 2026, every BL 00h-1Fh with BH 00h-07h in the emulator:

- BL=01h (refresh rate set, get and list) and BL=02h (mode list and mode information) return the same
  results in all four; S3 changed nothing there.
- The query (BL=00h BH=00h) differs only in its version number (0010h, 0411h, 0B10h, 0C10h).
- The only addition of relevance is BL=00h BH=01h in the Trio3D and Trio3D/2X BIOSes: the BIOS build
  date in BCD, read from the ROM header. No program or driver is known to use it, so it brings
  nothing.
- BL=03h-05h of the Trio3D/2X BIOS work on that chip's own registers and do not apply here.

None of them is ported: they bring nothing for this card. Windows compatibility also argues for
leaving 4F14h as it is: the Windows 9x S3 driver and S3's utilities were written against these BIOSes,
and a driver or utility may check the query's version (0010h) and expect the 2.04.07 behaviour, so a
changed version or added subfunctions could break them for no gain.

## Omitted: 1-cycle linear addressing (CR87 bit 1, SR15 bit 7)

The Trio64V2 datasheet (section 3.5) describes a faster linear addressing path: CR87 bit 1 = 1
enables 1-cycle linear addressing of video memory, "the memory must be capable of supporting this
mode", and the default with SR0A bit 7 and SR15 bit 7 set is 2-cycle operation. It was tried on top
of the booster in 640x480x8 (101h) with a write benchmark and a 320 KB pattern check:

| SR15 bit 7 | CR87 bit 1 | Write speed | Data errors |
| --- | --- | --- | --- |
| 0 | 0 | 83683 KB/s | 0 |
| 1 | 0 | 83683 KB/s | 65536 |
| any | 1 | hang | - |

There is no speed gain with this card's memory, SR15 bit 7 corrupts data and CR87 bit 1 hangs the
machine, so neither bit is set by the ROM. The Trio64V+ datasheet (SR15 bit 7, "2 CYC MWR") says the
2-MCLK write "can allow 2 MCLK operation for MCLK frequencies between 55 and 57 MHz"; the ROM's MCLK of
59.96 MHz at the time (p9-p25) is above that window, which fits the data errors.

## Known remaining items

- The 8x14 font is missing in the BIOS (S3COMPAT WARN 01 for AX=1130h BH=2 and mode 10h). A TSR
  supplies it: [8x14 font support as a TSR](https://www.bttr-software.de/products/fix8x14/), with the
  same font as the S3 Trio64.
- An LFB is offered on the planar mode 104h (S3COMPAT WARN 20), as in stock and the reference.
- Mode 106h runs at 108 MHz, above the datasheet single-clock limit (S3COMPAT WARN 02).
- S3COMPAT WARN 80 in 012Eh, 010Fh, 0131h and 0134h: End Horizontal Blank is 00h, so CR86 = 00h cannot
  be 1 less (V2-REG-3). The reference and the stock 2.04.11 set the same registers in 012Eh and 010Fh;
  0131h and 0134h get it from the ROM's 320x240 timing (the reference and 2.04.11 have 2Fh there).
- S3COMPAT WARN 82 in 012Ah (640x480x24): DCLK 75.16 MHz, 3 x 25.05 MHz, above the 75 MHz packed 24
  limit (02), and L1 (CR90/CR91) FFh, 2048 bytes per line where 1920 need EFh (V2-REG-4, 80); both as
  in the reference.
- These five modes show a clean picture on the card (edges and line ends, S3COMPAT and VBESHOW /R,
  30 October 2026, and again with p27 in the 11 November 2026 run, `results/86C775.ZIP`), so the
  emulator test `s3compat_full` accepts the five lines. Every graphics mode VBESHOW /A shows is
  clean on the card with p18 in plain DOS (30 October 2026).
- Cross-checked against the card's stock 2.04.11 (11 November 2026; this bullet is from disassembly of
  the stock ROM and stays out of the clean-room docs): run in the emulator
  ([`reference/775/2_04_11.bin`](../reference/775/2_04_11.bin), SHA-256 2daa1166...), 2.04.11 programs the
  same CR86 = 00h with End Horizontal Blank 00h in 012Eh and 010Fh, and the same CR91 = FFh in 012Ah.
  In its disassembly it never writes CR86 (no 86h CR index anywhere; CR86 = 00h is the power-on
  default), and it computes the L1 (CR90/CR91) at C000:D7F0-D832 from the mode entry's padded line
  length: 2048 bytes in 012Ah, giving FFh, where V2-REG-4 counts the 1920 displayed bytes (EFh). So
  S3's own later BIOS violates V2-REG-3 and V2-REG-4 exactly as ours does, and with the clean picture
  on the card the two rules as S3COMPAT encodes them are confirmed not to harm this card. The
  WARN 80/82 lines stay until an owner decision.
- VBE 4F15 keeps interrupts off for the whole call (p19, [#49](https://github.com/perchrh/trio64-vbios-tools/issues/49)):
  66 ms for BL=00h on the card (S3COMPAT /V, 1 November 2026), longer for an EDID read. The system
  clock loses ticks and a serial mouse or modem may lose bytes meanwhile. Kept: 2.04.07 turns on
  memory-mapped I/O (CR53 bit 4) at 5D0Ah and restores it at 5D50h, so for the whole call the upper
  part of the A0000 window is S3's register space; with interrupts on, an interrupt handler that draws
  there (a mouse cursor in a graphics mode) would write the graphics engine's registers. The serial
  port register also answers at port E2h or E8h, but which one the board's strapping decides (PD25,
  CR6F), so a BIOS cannot rely on it. A shorter window would turn memory-mapped I/O and interrupts off
  and on around each of the six accesses to MMFF20h in S3's DDC code: [#117](https://github.com/perchrh/trio64-vbios-tools/issues/117).
  Decided 8 November 2026: no patch to any of our ROMs (the same holds for the 764 and 765 ROMs,
  whose DDC paths have the same whole-call behaviour); the behaviour is documented for the clean-room
  implementation instead ([`clean-room.md`](clean-room.md) "Scope", milestone 7), and the patched ROMs
  keep their current whole-call behaviour (race review of 1 November 2026).
- The BIOS writes SR04 = 03h in text modes where IBM writes 02h; bit 0 is reserved on the VGA and
  reads back as 0 on the card, so programs see the IBM value.
- From the code review of 31 October 2026, kept as they are (the fixed items are #86, #87, #88; the
  items of the other two ROMs are in their documents):
  - Duplicated code: `p12ext.asm` keeps its own copies of the font load and the mode 13h scroll that
    `font32.asm` and `scr13.asm` hold for the other ROMs, and `vhooks.asm`/`vext.asm` repeat
    `wincheck.asm` and the fast 4F05 path. A fix to one copy must go to the other (p21 was made twice).
  - Several Trio64V2 blocks give their address both as `org` in the .asm and as a number in
    `s3patch.py` BLOCKS (wincheck, p19, hooks, p12ext, crtc240, vbe4f06; vhooks and vext on the
    Trio64V+), not once in `bios.inc`. Moving a block means editing both.
