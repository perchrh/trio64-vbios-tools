# Trio64V+ ROM (765): fixes and improvements

What 1.03-08-pN (the level in [`common/version.inc`](../common/version.inc)) changes against S3's Trio64V+ BIOS 1.03-08, each
with the issue that has the details. Most p1 changes are backports from the Trio64V2 ROM
([`docs/775-changes.md`](775-changes.md)): the issue is the Trio64V2 one, which carries the label 765. p2 fixes
faults of 1.03-08 itself. The build, what does not apply to the Trio64V+ and why, the per-call costs and
the card runs are in [`docs/765-rom.md`](765-rom.md).

| Change | Level | Issue | How |
| --- | --- | --- | --- |
| 32-bit video memory stores: S3/VESA mode set clear, VGA mode set clear, font load into plane 2, mode 13h scroll, text scrolls (full width, window moves and blank fills), planar scrolls, AH=09h text | p1 | [#60](https://github.com/perchrh/trio64-vbios-tools/issues/60), [#61](https://github.com/perchrh/trio64-vbios-tools/issues/61), [#62](https://github.com/perchrh/trio64-vbios-tools/issues/62), [#51](https://github.com/perchrh/trio64-vbios-tools/issues/51) | Every routine these patches replace is in 1.03-08 byte for byte: `s3vpatch.py` checks the same signatures as `s3patch.py`, at other addresses, and assembles the same files (`clear32.asm`, `p13*.asm`) with the 1.03-08 addresses of [`rompatch/vplus/bios.inc`](../rompatch/vplus/bios.inc). wmove and bfilla use the dead bytes after the clear and font load jumps, as in 2.04.07; the rest is in the free block 7AE0h-7D2Dh. |
| Booster: the 64 KB linear window at A0000h in banked packed modes | p1 | [#47](https://github.com/perchrh/trio64-vbios-tools/issues/47) | On at the end of a banked 4F02 and at the first bank switch (4F05 or the window function), as 2.04.07-p18 (`vhooks.asm`). The real base needs no save: 1.03-08 keeps the PCI base (bits 31-24) in CR6B from POST and writes it back to CR59 (CR5A = 00h) at every mode set (1015h); the mode set hook does it too, before the mode set. |
| Windows enhanced mode check | p1 | [#47](https://github.com/perchrh/trio64-vbios-tools/issues/47) | As 2.04.07-p17: no booster while INT 2Fh AX=1600h reports Windows in enhanced mode, asked once per mode set (CR6D = 01h marks the refusal; 1.03-08 does not use CR6D). |
| Fast 4F05h set window | p1 | [#59](https://github.com/perchrh/trio64-vbios-tools/issues/59) | At the INT 10h entry (`vext.asm`): 6 port writes where 1.03-08 needs 10 (the dispatcher unlocks CR38/CR39 twice and saves, sets and restores SR08). 1.03-08 neither keeps the bank at 0040:04FE nor refuses 4F05 with linear addressing on, so neither does the fast path. |
| Attribute controller flip-flop reset after the mode set | p1 | [#52](https://github.com/perchrh/trio64-vbios-tools/issues/52) | In the mode set hook, for AH=00 and 4F02. |
| The 32 KB twice in a 64 KB image (`SIZE765=64`), for boards that map either half of a 64 KB EEPROM | p1 | [#78](https://github.com/perchrh/trio64-vbios-tools/issues/78) | `s3vpatch.py --size 64`; the PCI ROM header declares one 32 KB image. |
| MCLK build option (`MCLK=`, `MEMTYPE=edo1, fpm`) | p1 | [#112](https://github.com/perchrh/trio64-vbios-tools/issues/112) | Sets one entry of the MCLK table, at most 60 MHz (MEM-1); README "MCLK build option". |
| 4F02 refuses a mode that does not fit the video memory | p2 | [#107](https://github.com/perchrh/trio64-vbios-tools/issues/107) | After the mode lookup (4924h), 4F01's own rule (C000:4898): BytesPerScanLine x YResolution, x 4 in 16 colours, in 64 KB units, must be below the memory size from CR36. Otherwise AX = 014Fh and nothing changes, as for an unknown mode. 1.03-08 set them: with 2 MB 118h, 119h, 11Ah, with 1 MB also 107h, 112h, 115h-117h, 120h. |
| The VBE functions keep the 32-bit registers | p2 | [#108](https://github.com/perchrh/trio64-vbios-tools/issues/108) | The dispatcher (47CDh) calls each function between PUSHAD and POPAD; the functions return through the INT 10h frame, so no result changes. 1.03-08 handed back EAX, ECX and EDX with changed upper halves after 4F06. |
| No interlaced timing | p2 | [#68](https://github.com/perchrh/trio64-vbios-tools/issues/68) | 118h (1024x768x16M), 119h/11Ah (1280x1024x32K/64K) and 120h (1600x1200) exist only interlaced on the Trio64V+ (CLK-1: 50 MHz at 32 bpp, 80 MHz at 15/16 bpp, 135 MHz clock-doubled 8 bpp; their 60 Hz timings need 65, 108 and 162 MHz). They leave the mode table (0128h, S3 modes 78h-7Ch) and the VESA list (4C13h with 4C51h); the S3 numbers 207h-213h move up behind the first FFFFh. The interlaced last entries of the 1024x768 and 1280x1024 refresh lists (055Ah, 0587h, 0605h, 0656h) are cut off by an end mark on the entry above, so refresh index 0 gives the lowest non-interlaced rate. As in the Trio64 ROM. |
| 10Dh-10Fh with the DCLK VCO in range | p2 | [#113](https://github.com/perchrh/trio64-vbios-tools/issues/113) | The DCLK at 25.06 MHz (VCO 200.5 MHz) in place of 12.62 MHz (VCO 101 MHz), halved by SR01 bit 3 after the mode set; [`docs/765-rom.md`](765-rom.md), "10Dh-10Fh". Open until the picture is checked on a card. |
| Interrupts off in the sequencer reset of 10Dh-10Fh (`msx`) | p3 | [#116](https://github.com/perchrh/trio64-vbios-tools/issues/116) | `cli` from reading the sequencer index to putting it back; the popf at the end of `msx` restores IF. |

Not carried, and why (details in [`docs/765-rom.md`](765-rom.md), "Does not apply to the Trio64V+"): the FIFO fetch fix
([#53](https://github.com/perchrh/trio64-vbios-tools/issues/53)), CR23 before CR26 ([#50](https://github.com/perchrh/trio64-vbios-tools/issues/50)), the POST delay ([#48](https://github.com/perchrh/trio64-vbios-tools/issues/48)) and the DDC fixes ([#49](https://github.com/perchrh/trio64-vbios-tools/issues/49), [#86](https://github.com/perchrh/trio64-vbios-tools/issues/86)), which concern Trio64V2
registers or 2.04.07 code; the LFB fixes of the booster and 4F06 BL=3 ([#55](https://github.com/perchrh/trio64-vbios-tools/issues/55)), VBE 2.0 functions; the
black level ([#63](https://github.com/perchrh/trio64-vbios-tools/issues/63)), a Trio64V2 register; 1600x1200 at 60 Hz, beyond the chip's clock.
